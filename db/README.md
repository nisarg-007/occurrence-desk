## Running the migrations

Needs a real Postgres 16 (`docker compose up` once Wasim's stack lands, or any Postgres 16
instance — RDS, or one on your laptop):

```bash
export DATABASE_URL=postgresql+psycopg://occdesk:occdesk@localhost:5432/occdesk
python -m venv .venv && . .venv/bin/activate && pip install -r requirements-dev.txt

alembic -c db/alembic.ini upgrade head       # apply everything
alembic -c db/alembic.ini downgrade base     # the CI round-trip check (§2.3)
alembic -c db/alembic.ini upgrade head
```

`alembic -c db/alembic.ini upgrade head --sql` renders the migration as plain SQL without
touching a database — the fastest way to review what a migration will actually do, and what
this repo's own verification (no live Postgres available in this environment) relied on.

## Seeding

```bash
python -m db.seed.hazard_categories   # taxonomy + severity weights (idempotent)
python -m db.seed.users               # analyst / manager / admin, local only
python -m db.seed.load_bts /path/to/T_ONTIME_REPORTING_2022_12.csv
```

Download the BTS file from
<https://www.transtats.bts.gov/DL_SelectFields.aspx?gnoyr_VQ=FGJ&QO_fu146_anzr=b0-gvzr> —
December 2022 first (Sowmya's Winter Storm Elliott replay needs exactly that month).

`load_bts` is safe to re-run against a month you've already loaded: `COPY` can't express
`ON CONFLICT`, so every load lands in a `TEMP` staging table first and merges with
`INSERT ... ON CONFLICT DO NOTHING` against the real tables.

## Keeping `reports.priority` fresh

`reports.priority` is denormalised (see `priority.py`'s docstring for why it can't be a
Postgres `GENERATED` column). `SqlRepo.assign` calls `refresh_priorities(session,
report_id=...)` after a manager flag changes a report's score. Two gaps that are still open
for M2/M3, named rather than hidden:

- nothing yet calls `refresh_priorities` after Smit's worker writes a new hazard or
  `link_best_candidate` writes a new flight link — that wiring belongs in the worker's
  write path once it exists.
- pure recency drift (a report ages by a day; nobody touches it) needs a periodic
  `refresh_priorities(session)` with no `report_id` — a cron/scheduled task, not built here.

## What's verified vs. what's pending a live Postgres

This environment has no Docker/Postgres available, so the checks actually run were:
model metadata sanity (`tests/unit/test_db_models.py`), a logic cross-check between
`priority.py`'s SQL and `ranking.py`'s Python (`tests/unit/test_priority_sql_matches_ranking.py`),
Postgres-dialect SQL compilation for both migrations and the linkage query (no connection
needed — `alembic ... --sql` and `Select.compile(dialect=postgresql.dialect())`), and
`ruff` / `mypy` over the whole `db/` package. Genuinely pending a live instance, per the
work pack's own M1/M2/M3 bars — tracked in `docs/measurements.md`:

- `alembic upgrade head` / `downgrade base` against a real database (not just `--sql`)
- `make db-load` timing and an exact row-count match against the source CSV

- the PITR restore rehearsal (§2.5)
- the connection-pool ceiling under Sowmya's replay
